# Project Memory in the dashboard — tab, posture, and suggestions

Date: 2026-07-03
Status: Approved (design)
Builds on: `2026-07-01-project-memory-design.md` (the memory model this feature surfaces)

## Motivation

The bridge already has a curated project-memory system: durable facts are captured
after a turn (a Haiku pass proposes them → the user Keeps/Skips), stored in SQLite,
and injected into every turn's system prompt scoped to `(owner, project, branch)`.
Today that system is only visible through a **global** Memory view — there is no
per-project surface, no per-project control over how memory behaves, and the stored
facts are never used to help the user decide what to do next.

This feature makes memory legible and controllable **per project, on the desktop
dashboard**, and puts the stored facts to work as prompt suggestions.

## Goals

1. A **Memory tab** inside the dashboard project modal (`AnalyzeModal`) that shows
   the memory the bridge is keeping *for that project*, plus a short explainer that
   memory is being handled.
2. A **per-project posture** — `Ask` / `Auto` / `Off` — giving the user explicit
   permission control over memory capture and injection for each project.
3. **Prompt suggestions** derived from a project's memory, shown automatically in a
   new session's empty state, that inject into the composer on click.

## Non-goals

- No Mini App changes. This is dashboard-only. (The Mini App's global Memory tab and
  the backend model are untouched except for the shared, additive backend below.)
- No semantic/embedding retrieval. Suggestions are generated by a cheap Haiku pass
  over the already-rendered memory pack, not by vector search.
- No change to the memory data model (types, scopes, cascade) beyond the additive
  `memory_mode` per-project setting.

## Decisions (locked during brainstorming)

- **Permission model:** per-project **posture** with three modes — `Ask` (today's
  Keep/Skip gate), `Auto` (proposals auto-kept, no gate), `Off` (no capture, no
  injection). Subsumes a plain on/off.
- **Surfaces:** dashboard only.
- **Suggestions:** **auto** on a new session — run the Haiku pass and show up to 3
  suggestion chips in the empty state (cost-capped by a per-project cache; see below).

## Feature 1 — Per-project memory posture (backend, net-new)

### Storage

Add to `bridge/project_config.py`, alongside `run_cmd`/`prod_url`:

- `memory_mode(project: str) -> str` — returns `"ask" | "auto" | "off"`, defaulting
  to `"ask"` when unset. **Always reads the bare-project key** (branch `None`): the
  posture is a project-wide consent decision, not per-branch. (`run_cmd`/`prod_url`
  stay per-branch; only `memory_mode` is forced project-wide.)
- `set_memory_mode(project: str, mode: str) -> str` — validates `mode ∈ {ask, auto,
  off}` (falls back to `ask` on anything else), writes the bare-project key via the
  existing `_set_field(project, None, "memory_mode", mode)`.

The global `config.MEMORY_ENABLE` remains the master gate. Effective behavior =
`MEMORY_ENABLE` **and** the per-project posture. If the master flag is off, posture
is irrelevant (memory fully disabled).

### Enforcement (`bridge/runner.py`)

Resolve the project key with the existing `_project_key(chat_id, cwd)`, then:

- **Injection** — in `_memory_pack_for(chat_id, cwd)`: if the resolved posture is
  `off`, return `""` (no pack). Otherwise render the pack as today.
- **Capture** — in `_capture_async(...)`:
  - `off` → return early, skip capture entirely.
  - `ask` → call `memory.propose(...)` as today (writes `status="candidate"`).
  - `auto` → call `memory.propose(..., auto=True)`.

`memory.propose(...)` gains an `auto: bool = False` keyword: when `True`, rows are
written with `status="active"` instead of `"candidate"` (skipping the human gate);
the `memory_candidate` event is still appended so the transcript shows what was
recorded. Everything else (parsing, reconciliation, supersedes) is unchanged.

Note: the blocking Telegram path (`handle_task`) currently passes `cwd=None` to
capture; posture there resolves against the chat's current project, consistent with
how that path already scopes injection. No change to that behavior in this feature.

### Endpoint

Thread `memory_mode` through the **existing** `/local/project/settings` route in
`bridge/dashboard/server.py` — no new settings endpoint:

- **GET** (`server.py:334-340`): add `"memory_mode": project_config.memory_mode(rel)`
  to the returned object. (Ignore `branch` for this field.)
- **POST** (`server.py:497-502`): if `"memory_mode" in body`, call
  `project_config.set_memory_mode(rel, body["memory_mode"])` and include the result
  in the response.

## Feature 2 — Memory tab in `AnalyzeModal` (dashboard frontend)

### Integration

`bridge/dashboard/web/src/components/hud/AnalyzeModal.tsx` is already tabbed. Add an
8th tab, `MEMORY`:

- Extend the `Tab` union (`AnalyzeModal.tsx:23`).
- Push an entry into the `tabs` array (`AnalyzeModal.tsx:141-149`), with an optional
  badge = pending-candidate count.
- Add a body branch (`AnalyzeModal.tsx:222-249`) rendering a new
  `MemoryTab` component that receives `project` (the rel path the modal already holds).

### Contents (`MemoryTab`, new component)

Project-scoped, reusing existing endpoints and the visual language of `MemoryView.tsx`
/ `MemoryCandidateCard.tsx`:

1. **Status strip**
   - Posture segmented control: `Ask | Auto | Off`. Reads `memory_mode` from
     `api.projectSettings(project)`; writes via `api.setProjectSettings(project,
     {memory_mode})`.
   - One-line explainer: *"Facts kept here are injected into every session in this
     project, so Claude knows its conventions, decisions, and goal without
     re-deriving them."*
   - Counts: N active, N pending. When posture is `off`, the strip shows a muted
     "Memory is off for this project" note and the lists collapse.
2. **Pending candidates** — `api.memoryItems(project, "candidate")`, each rendered
   with inline **Keep/Skip** (`api.memoryCandidate(id, "keep"|"skip")`). This gives
   the `Ask` gate a durable home instead of only the transient transcript card.
   (Empty in `Auto`/`Off`.)
3. **Active memories** — `api.memoryItems(project, "active")`, grouped by type, each
   with Pin/Unpin (`api.memoryPin`) and Delete (`api.memoryStatus(id, "archived")`).

No new backend for this feature — every endpoint already exists and already accepts
`project`. `api.ts` `ProjectSettings` type (`api.ts:184-188`) gains
`memory_mode?: string`.

## Feature 3 — Memory-driven prompt suggestions (dashboard)

### Trigger & placement

When the dashboard shows a **new session's empty state** (a session with no turns)
for a project whose posture is not `off`, automatically fetch suggestions and render
up to 3 chips in that empty state. Clicking a chip **injects** its text into the
composer via the existing `feed()` → `inject` channel (`App.tsx:333-337`,
`Composer.tsx:96,123-129`) — it never auto-sends; the user reviews and sends.

### Endpoint (new)

`POST /local/memory/suggest` in `bridge/dashboard/server.py`, body `{project}` (or
`cwd`/`cwd_rel`, matching the `/local/project/settings` resolution). Handler:

1. Resolve `rel` project + `chat` (owner) as other `/local/*` routes do.
2. If `MEMORY_ENABLE` is off, posture is `off` → return `{"suggestions": []}`.
3. Render the project's pack via `memory.render_pack(chat, rel, branch)`. If empty
   (no memory yet) → return `{"suggestions": []}`.
4. **Cache** keyed `(chat, rel, store.namespace_version(chat, rel, branch))`. On hit,
   return the cached list. This caps cost: the Haiku call only actually runs when the
   project's memory changed since last time, even though the client asks on every new
   session.
5. On miss, run a cheap Haiku pass:
   `runner.run_blocking(chat, PROMPT, model="haiku", skip_pack=True)`, where `PROMPT`
   embeds the rendered pack and asks for **exactly 3 concrete next-step prompts** the
   user could send, as a strict-JSON array of short strings. Parse tolerantly (reuse
   the `_parse_ops`-style fenced-JSON extraction pattern from `memory.py`); on any
   failure return `{"suggestions": []}`. Cache and return.

Generation lives next to the other memory logic (a `suggest()` in `bridge/memory.py`,
with the cache), mirroring how `propose()`/`render_pack()` are organized. The suggest
prompt is grounded in the pack's `goal`/`convention`/`gotcha` facts so suggestions are
about *this* project.

### Client

`api.ts` gains `memorySuggest(project: string): Promise<string[]>` → POST
`/local/memory/suggest`. The empty-state component calls it once per new session
(guarded so it fires once per session mount, not on every re-render) and renders the
chips; `onFeed`/`feed` pushes a chosen suggestion into the composer.

## Data flow (suggestions, end to end)

```
new session empty state (project P, posture ≠ off)
  → api.memorySuggest(P)
    → POST /local/memory/suggest {project: P}
      → memory.suggest(chat, P, branch)
          cache hit on (chat, P, namespace_version)? → cached list
          else render_pack → Haiku (run_blocking, skip_pack) → parse → cache
      → {suggestions: [...≤3]}
  → chips rendered; click → feed(text) → composer textarea (review, then send)
```

## Error handling & edge cases

- **Off posture:** no injection, no capture, no suggestions. Tab shows the muted
  "off" state; lists hidden.
- **No memory yet:** suggest returns `[]`; empty state shows no chips (no error, no
  Haiku spend).
- **Haiku/parse failure:** suggest returns `[]`, swallowed like `propose` — never
  blocks or errors the session start.
- **Auto mode + existing candidates:** switching a project to `Auto` does not
  retroactively keep existing `candidate` rows; it only affects future captures.
  (Existing candidates remain Keep/Skip in the tab.)
- **Cost guard:** the per-`(project, namespace_version)` cache means repeatedly
  opening new sessions without changing memory does not re-spend on Haiku.

## Testing

- **`project_config`** (`tests/`): `memory_mode` defaults to `ask`; set/get round-trip
  for each mode; invalid value coerces to `ask`; posture is project-wide (setting it
  on `project` is read back regardless of branch).
- **`runner`/`memory` enforcement:** with a fake capture `run`, assert `off` skips
  capture and yields an empty pack; `ask` writes `candidate`; `auto` writes `active`.
  (Follows the existing `memory.propose` test style with an injected `run`.)
- **`memory.suggest`:** with an injected `run` returning JSON, assert parsing → ≤3
  strings, cache hit avoids a second `run` call, empty pack short-circuits to `[]`,
  malformed output → `[]`.
- **Endpoints:** `/local/project/settings` GET includes `memory_mode` and POST sets
  it; `/local/memory/suggest` returns `{suggestions}` and `[]` when off/empty.
- Frontend is verified by build + manual check (no component test harness today).

## Build / deploy

Backend changes are picked up on the next bridge start. Frontend: edit
`bridge/dashboard/web/src`, then rebuild the served dist with
`npm --prefix bridge/dashboard/web run build` (per the project's build note — the
dashboard serves a prebuilt `dist`). Do not restart the bridge mid-session unless
asked.
